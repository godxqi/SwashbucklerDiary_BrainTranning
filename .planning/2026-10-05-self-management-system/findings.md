### ⚠️ 过程中被用户纠正的两次（重要教训）

**第 1 次**：我第一轮就直接问「日课录入形式该用哪种 UI 形态」，被用户打断：

> "不, 你跳过了需求确认, 我们应该**依次确认日课 / 周课 / 月课 / 表 / List 中我期待的录入形式与效果**, 再对应到具体细节上. 而且**回环总图这里的回归我希望可以自动化**"

→ 教训一：**先逐板块确认「形式与效果」，再谈实现细节**
→ 教训二：**"回环自动化"是贯穿性诉求**，不是某板块的细节，要在每一处回环上体现

**第 2 次**：用户进一步明确这是「顺序/粒度问题」，要求**先定整体交互哲学 / 架构，再逐块细化**

→ 教训三：**自上而下** —— 第一身份 → 导航骨架 → 逐板块形式与效果 → 实现细节

## 研究发现（代码库探索）

### 导航与布局
- **唯一真源**：`src/SwashbucklerDiary.Rcl/Layout/MainLayoutBase.cs` 第 21-27 行 `navigationButtons`（`List<NavigationButton>`）
- `IsPermanentPath`（第 71-72 行）由它反推 → **导航栏显隐的开关**
- `PageCacheContainer.PermanentPaths` 也由它驱动 → 改导航会**联动页面缓存策略**
- 手机底栏：`Rcl/Layout/MainLayoutBottomNav.razor`（MASA `<MBottomNavigation>`，仅 `Breakpoint.Xs && IsPermanentPath` 时显示）
- 桌面侧栏：`Rcl/Layout/MainLayoutNavDrawer.razor`（`SmAndUp && IsPermanentPath`）
- `Rcl.Hybird/Layout/MainLayoutBase.cs` 只重写 `OnInitializedAsync` + `HandleSchemeActivation`，**不碰 nav 列表** → 直接改 Rcl 版即可
- `NavigationButton(Text, Icon, Href)`；Text 走 `I18n.T(key)`
- **`NavigateTo("")` 出现在**：`PageCacheContainer`(×2)、`AppLock`、`PrivacyModePage` → 改根路由后全部落到新看板，需逐一回归

### 数据层：新增一张表的完整链路（5 处）
1. **模型**：`Shared/Models/XModel.cs` 继承 `BaseModel`（`Guid Id` + `CreateTime` + `UpdateTime`）
2. **仓储**：`Rcl/Repository/XRepository/XRepository.cs` + `IXRepository.cs`，继承 `BaseRepository<T>`
3. **建表**：`Rcl/Extensions/ServiceCollectionExtensions/AddSqlsugar.cs` 第 176-186 行 `Type[] types = {...}` → `CodeFirst.InitTables(types)`，**加进数组即自动建表**
4. **DI**：`Maui/Extensions/ServiceCollectionExtensions/AddDependencyInjection.cs`
5. **业务服务**：`Rcl/Services/Data/XService/`

要点：
- `dataConfigs` 排除日志库 → **新表会同时建在主库和隐私库**
- `BaseRepository.Context` 按 `SettingService.GetTemp(it => it.PrivacyMode)` 切换连接 → 新仓储**自动获得隐私模式支持**
- 已有通用方法：`CountAsync()`、`UpdateAsync(entity, columns)`
- **迁移**：`Rcl/Services/VersionUpdataManager/VersionUpdataManager.cs`，`_versionHandlers`（`SortedDictionary<Version, Func<Task>>`）+ `InitializeVersionHandlers()`
- SqlSugar `InitTables` 对已存在的表**补列不删列**

### 页面路由
- Blazor `@page` 约定，**无集中注册表**
- `Maui/Routes.razor`：`AdditionalAssemblies = [typeof(Rcl._Imports).Assembly, typeof(Rcl.Hybird._Imports).Assembly]` → **在 `Rcl/Pages/` 下新建 `.razor` 加 `@page` 即自动可路由**
- 页面基类三层：`MyComponentBase` → `ImportantComponentBase`（`ReadSettings()`/`OnResume()`/`NavigateToBack()`）→ `DiariesPageComponentBase`（`Diaries`/`Tags`/`QueryDiariesAsync`）

### 备份与导出（关键结论）
| 通道 | 实现 | 覆盖新表 |
|---|---|---|
| DB 备份/恢复 | `DiaryFileManager.ExportDBAsync` / `ImportDBAsync` —— **整库文件复制** | ✅ **自动覆盖** |
| WebDAV 备份 | 复用 `ExportDBAsync` | ✅ |
| 局域网同步 | 复用备份/导出管线 | ✅ |
| JSON/MD/TXT/XLSX 导出 | `ExportJsonAsync(List<DiaryModel>)` 等，**只序列化 `DiaryModel`** | ❌ **缺口** |

→ 整库备份天然安全；唯一缺口是"可读导出"，阶段 4 补 `review.json`。

### 设置项
- `Rcl/Services/SettingService/Setting.cs` 是**纯 POCO**（60+ 属性）
- `ISettingService.Get<T>(expr)` / `SetAsync(expr, value)` 走 `IPreferences`
- **加一个属性 = 加一个设置项**，无需迁移；自动纳入 `settings.json` 备份
- 配套组件 `SettingSwitch.razor` 只需 `SettingKey="@nameof(Setting.X)"`

## 设计方案详解

> 来源：架构 agent 的完整代码库探索 + 设计。**这是实施的直接依据**（原稿曾只在 `~/.claude/plans/` 里，现已迁移到此处）。

### 数据模型（12 张新表 + 2 处既有模型扩展）

#### 既有模型扩展

```csharp
DiaryModel  += Kind (ReviewKind?, 默认 null = Free)
   // enum ReviewKind { Free=0, Daily=1, Weekly=2, Monthly=3 }
TagModel    += Kind (TagKind { Normal=0, Trigger=1, Category=2 })
   // 让"触因"成为一等公民：计数/增删/芯片选择全部复用现有标签管线
```

#### 日课（1 张）

```
DailyReviewModel : BaseModel
  DiaryId, Date(date, 唯一索引), Mood(1/8 情绪), Category(点选类别),
  AffirmationIds(JSON List<Guid>), Energy(int?),
  MicroFailure(string?), IsCompleted(bool)
```

#### 周课（3 张）

```
WeeklyReviewModel : BaseModel
  Year, WeekOfYear(唯一), StartDate, EndDate, DiaryId?,
  FrequencyConfirmed(bool), GoalsConfirmed(bool), IsFinalized, FinalizedTime

WeeklyGoalModel : BaseModel                    // 需求 5 结构化目标卡
  WeeklyReviewId, Domain(GoalDomain{Emotion,Work,PersonalDevelopment}),
  Content, MacroGoalId?,
  SmartSpecific/SmartMeasurable/SmartAchievable/SmartRelevant/SmartTimeBound
      (string?, 可选展开),
  Status(GoalStatus{Pending,InProgress,Done,Dropped}), SettledWeekOfYear?

StumblingBlockModel : BaseModel                // 需求 4 数频率 + 人工判定
  Year, WeekOfYear, Category, Description?, SourceDiaryId?,
  Verdict(BlockVerdict{Undecided,StumblingBlock,Environment,Rejected})
```

> **「数频率」的数据源就是这张表**：日课录一条"微观失败" → 自动落一行 `Verdict=Undecided` → 周课按 `Category` GROUP BY 出频次 → 用户逐条翻 `Verdict`。

#### 月课（3 张）

```
MonthlyReviewModel : BaseModel
  Year, Month(唯一), DiaryId?,
  Step31Done, Step32Done, Step33Done, Step34Done (bool),   // 四步闸门
  Step33Note(自我补偿产出), IsFinalized, FinalizedTime

LimitingBeliefModel : BaseModel                // 3.1 三列审视
  MonthlyReviewId, Assertion, SupportingEvidence, CounterEvidence, Utility

EnemyModel : BaseModel                         // 3.4 敌人表（三列三行）
  MonthlyReviewId, Goal, BlockingBehavior, DeepBelief, WeeklyAction
```

> **3.2 提炼短语不建表** —— 产物直接写进 `SelfAffirmationModel`（复用需求 10 的库）
> **四步闸门实现**：3.1→`LimitingBeliefModel.Count > 0`；3.2→本次新增 `SelfAffirmationModel > 0`；3.3→`Step33Note` 非空；3.4→`EnemyModel.Count > 0`。不满足则"下一步"按钮禁用 + 提示还差什么

#### 库表（5 张）

```
VirtueEntryModel : BaseModel                   // 需求 8 三个优点表
  Kind(VirtueKind{Positive,Gratitude,Achievement}), Content, Date,
  SourceDiaryId?, IsAchieved, AchievedTime?

SelfAffirmationModel : BaseModel               // 需求 10 自我肯定库
  Content, Source?, RepeatCount(int), LastRepeatedTime?, IsActive(bool)

ArchiveItemModel : BaseModel                   // 需求 9 / 7.4 归档区（四个 List）
  Kind(ArchiveKind{Environment,RejectedBlock,...}), Content,
  OccurrenceCount(int), LastOccurredTime,
  SourceWeeklyReviewId?, FedBackToWeekOfYear?

MacroGoalModel : BaseModel                     // 需求 11 三大宏观方向
  Domain(GoalDomain), Title, Description?, IsActive

StateRecordModel : BaseModel                   // 需求 7 完整表单
  OccurredTime, Scene, TriggerTagId?(触因 → TagModel),
  Body, Mind, Emotion, Spirit, EmotionName(1/8),
  InvokedKind(InvokedKind{Virtue,Affirmation,MacroGoal}), InvokedId?,
  ActionNow
```

> 需求 8 的"可被调用"由 `StateRecordModel.InvokedKind + InvokedId` 支撑 —— 状态管理表能翻到某条优点/肯定/宏观目标，**双向可追溯**。

#### 读写分工

| 数据 | 存哪 | 理由 |
|---|---|---|
| 日课自由文本、周/月课长散文 | `DiaryModel.Content`（Markdown） | 可读 / 可导出 / 可搜索 |
| 情绪 / 类别 / 触因 / 肯定选择 | 新表 + `TagModel` | 要计数、要聚合 |
| 目标卡 / SMART / 状态 | 新表 | 要生命周期流转 |
| 优点表 / 归档 / 肯定库 | 新表 | 要计数、要被引用 |
| 自动摘要 | 写回 `Content` 的**受管区块** | 导出可读、正文自洽 |

**受管区块**：`<!-- review:facets:start -->…<!-- review:facets:end -->`，只替换区块内，**区块外用户手写内容原样保留**；区块不存在则追加到末尾。

### ⚠️ 由此确认的陷阱（**阶段 1 写查询前必读**）

老数据的 `Kind` 是 **NULL**，不是 0。SQL 里 `NULL = 0` 为 false，所以：

```sql
-- ❌ 匹配不到任何旧日记
WHERE Kind = 0
-- ✅ 正确写法（null 语义上就等于 Free / Normal）
WHERE Kind IS NULL OR Kind = 0
```

**因此 `Kind` 全程保持可空**（`ReviewKind?` / `TagKind?`），而不是规划里写的非空。
理由有两条：① SQLite 不接受没有默认值的 `NOT NULL` 补列，非空会让老用户的库**直接打不开**；
② 实测确认 SqlSugar 补的就是可空列。**null ≡ Free / null ≡ Normal 是本项目的既定语义**，
新写的每一处 `Kind` 过滤都必须同时接受 null。

## 🔬 阶段 3 实测与踩坑（2026-10-05）

### 1. ⚠️ 往真机库灌演示数据：Guid 末段必须凑满 12 位

写脚本时用 `PREFIX + "6%02d"` 拼 Guid，得到 `...-0000000000601`（末段 13 位）→
SqlSugar 读 `StumblingBlockModel` 时直接抛 **`Id bind error`**，整个周课页加载失败。

- **教训**：灌数据一律用 `"%012d" % n` 生成末段，别靠肉眼数位数。
- 附带收获：这条错**响亮地失败**了（日志里一条 Error + 页面明显异常），
  而不是静默给个错值——读链路的健壮性在这里是加分项。

### 2. ⚠️ 自搭的 flex 步进条会把宽度算飞（**别再自搭**）

月课页最初自己写了一版步骤条：`.review-steps{display:flex}` + `.review-step{flex:1}`。
真机量出来**每段 926px、整行 3734px**，而容器只有 2452px——第 4 段直接被挤出屏幕。
（用 PowerShell 读 PNG 的像素行确认的：黑段 54-979、灰段 989-1915、灰段 1925-2559。）

- **改用项目里已经跑通的芯片写法**（`MChipGroup` + `MChip`，`.review-chip-group` 自带
  `overflow-x:auto; white-space:nowrap`）之后正常，而且顺带能显示步骤名。
- **结论**：这个项目里「一排可点的东西」**统一用芯片**，别再自搭 flex 行。

### 3. ⚠️ i18n 漏键扫描的两个坑（第一版脚本两处都漏了，真机截图才暴露）

写了个脚本扫新代码用到的 key 和 `en-US.json` 对比。它连漏两批：

| 漏法 | 表现 | 修法 |
|---|---|---|
| 只匹配 `I18n.T("字面量")` | 项目里大量写法是 `I18n.T(x switch { A => "key", … })`，字面量**不在 `I18n.T(` 的正后面** → 归档区芯片显示英文 | 改成「按括号配对取出实参区间，再收里面的所有字面量」 |
| `"I18n.T("` 区分大小写 | **服务里的参数名是小写 `i18n`**（`ReviewSectionText.MonthlyLabels`） → 月课 3.2 的标题在正文里显示英文 | 改用正则 `[Ii]18n\.T\(` |

- 还有一处**不是脚本的错**：`monthlyTitleKeys` / `monthlyDescriptionKeys` 是数组里的字面量，
  既不是 `I18n.T(` 的实参、也不是 `const string`——这两组是后来单独核对的。
- **教训**：i18n 能不能漏，**只有真机截图说了算**；脚本只是辅助。

### 4. `InputDialog` 自带 `Text` 预填参数（编辑类对话框别忘了传）

`Components/DialogComponents/InputDialog.razor.cs` 里有 `[Parameter] string? Text`，
`HandleOnBeforeShowContent` 会 `internalText = Text`。
**不传就是给用户一个空白框**——优点表第一版的「编辑」就是这样，很容易让人以为内容丢了而重填覆盖。

### 5. 归档区的「计数」只对 7.4 有意义

`ArchiveAsync` 原本对所有 List 都做「同内容 → 次数 +1」。但文档只给 **7.4** 定了计数语义
（出口靠它数「不是偶发」）；7.1 那种地方把次数刷高只会让人误以为「这条观念我提过几次」。
→ 改成**只有 `ArchiveKind.MicroFailure` 才累加**。

### 6. 「回流」要回到的是**候选池**，不只是清单

文档 7.4 的出口原话是「累计 3 次 → **回到 2.1 重新进入候选池**」。

### 2. ⚠️ 截图工具自己有坑：DPI-unaware 只截得到 1/1.5 的屏幕，**最大化会让窗口比能截到的范围宽**

验证阶段 4 时一度以为统计页布局坏了（条形比卡片宽、数值消失），差点去改布局。**其实两个都不是**：

- 这台机器物理屏幕 3840×2160、Windows 缩放 150%；PowerShell 是 DPI-unaware，
  `PrimaryScreen.Bounds` 给的是 2560×1440，`CopyFromScreen` 只拿到**左上角那 2560×1440 物理像素**。
- `ShowWindow(SW_MAXIMIZE)` 让窗口变成 3840 物理 px 宽 = **2560 CSS px**，
  而能截到的只有左边 1707 CSS px → **截图里只有窗口左边 2/3，右边内容整块丢掉**。
- **怎么发现的**：拿阶段 1 就验过、主人手测通过的 `/library` 做对照 —— 它的入口按钮
  也只显示到「积极列表」，后面三个按钮根本不在画面里。**同一个"病"出现在没动过的页面上，
  就说明病在工具而不在代码。**
- **标定方法（值得复用）**：在页面上临时放一个 `400×40` 的纯红 `div`，截完图量它在图里有多少像素
  —— 这次量到 600×60，于是 `1 CSS px = 1.5 截图 px`，视口 = 2560/1.5 = **1707 CSS px**。
  有了这个比例才能把「图里的像素」换算回「CSS 像素」，再拿去做判断。
  （换算后：月课条 2376 CSS px 宽、填充 784 px = **正好 33%** —— 布局其实是对的。）
- **修法**：`snap-app.ps1` 不再最大化，改成 `SetWindowPos(...,1300,900,...)`
  （1300×900 虚拟 px 远小于能截到的 2560×1440，整窗都在画面里）。

### 3. 空文本框在截图里只有一条细下划线 —— 是**项目本来的样子**，不是 bug

状态管理表的 6 个文本框在截图里只有一条细线，一度怀疑输入框没渲染。
拿日课页（阶段 1 主人手测过、能正常输入）做对照：**一模一样**。
→ MASA 的 `MTextarea` 在本项目主题下就是这个观感（空的时候只有下划线）。

### 4. `FinalizeAsync` 要**先立旗再落盘**，否则「本周已完成」那行永远等不到

周课正文的受管区块里有一行「本周周课已完成」，它依赖 `review.IsFinalized`。
原来的顺序是「先 `SaveAsync` 落盘散文 → 再立旗」，于是**这一行永远写不进去**
（写正文时旗还没立）。改成先立旗再落盘；失败时把内存里的旗回滚，免得页面显示「已完成」而库里没有。

### 5. 判据要收口：一份私有拷贝迟早会长出第二份

`TriggerService` 里有个私有的「只填了触因」判据，阶段 4 的列表页又要用同一个判据。
→ 收口成 `ReviewModelExtensions.IsTriggerOnly()`（`ReviewModelExtensions` 本来就是放这类
「语义收口」的地方，`EffectiveKind()` 就在那儿）。
同理，`DomainText/StatusText/VerdictText` 在四个文件里各有一份，阶段 4 的服务要第五份时收口进了
`ReviewSectionText` —— 页面显示与「写进正文的生成式摘要」共用同一份，避免
「页面上写着环境原因、导出的正文里是别的词」这种最难发现的不一致。

### 6. 跨版本的外部校验：`Year * 100 + WeekOfYear` 合成键

失败行只有 `Year`/`WeekOfYear` 没有日期，按时间范围筛选就得把两个 int 合成一个单调的键去比大小
（周次最多 53，不会进位）。**真机实测 SqlSugar 能翻译这种列上的算术表达式**，
跨年区间一个 `BETWEEN` 就够，不用按年拆段。

## 阶段 6 的硬约束（改数据模型前必读）

### ① SqlSugar 的 `InitTables` 加列时**只加可空列，且从不删列、不改可空性**

- 实测 DDL（真机）：给 `WeeklyReviewModel` 加 `IsSkipped` 之后得到的是
  `` `IsSkipped` bit `` —— **没有 NOT NULL、没有默认值**，所以**老行读出来是 NULL**。
- 于是：**新加的非空值类型属性（`bool`/`int`/枚举）会让读取直接抛异常**：
  `JsonSerializationException: Error converting value {null} to type 'System.Boolean'`。
  不是只在补列那一刻炸，是**以后每次查出这行都炸**。
- **规矩：往这 12 张表里加字段，一律声明成可空**（`bool?` / `int?` / 枚举带 `?`），
  判定写 `== true` 这种显式比较。`Kind` 当初做成 `ReviewKind?` 就是这个原因，
  阶段 6 的 `IsSkipped` 忘了这条，真机验证第一轮就撞上了。
- 反过来的坑（阶段 5 埋的、阶段 6 才炸）：**把属性删掉不等于把列删掉**。
  老库里的列还在，而 SqlSugar **只加不删** → 模型里没有该属性 → INSERT 不会带它 →
  如果那列是 `NOT NULL`，**插入直接失败**。
  `VirtueEntryModel.IsAchieved`（`bit NOT NULL`）就是这么炸的，`AchievedTime` 同理（可空，侥幸不炸）。
  **删模型字段前，先确认库里那一列是否 NOT NULL；是的话要么把属性留回来，要么另写 DROP COLUMN 迁移。**

### ② 页面已经被缓存，`?Date=` 不能只在 `OnInitializedAsync` 里读

`PPageContainerReplacement` 会缓存页面实例，路由参数变化时**只重跑 `OnParametersSetAsync`**，
`OnInitializedAsync` 一辈子只跑一次。所以「从看板/菜单带着新日期再进同一个复盘页」，
光在初始化里读参数会**停在上一次那一天**。

规矩：**参数读取放 `OnParametersSetAsync`，并用一个 `appliedDate` 之类的水位挡住重复加载**
（父组件重渲染也会走这个方法）。`ArchivePage` 早先取巧用「本地状态为真源 + `To()` 只同步地址栏」，
阶段 6 改成「参数为真源」后两个入口（外部跳转 / 页内选日期）就都通了。

### ③ 日历标点只有桌面端有

`PMobileDatePicker`（在 `Masa.Blazor.MobileComponents.dll` 里，不是主 dll）**不支持 `Events`**。
`MultiSizeDatePicker` 只把它透给桌面端的 `DatePickerDialog`，手机端要靠页面上一句提示兜底。

## 阶段 6 的可复用做法

- **失败行按「描述优先、序号兜底」认领**（`StumblingBlockService.SyncFromDailyAsync`）：
  两轮认领——先按描述文本精确匹配（判定跟着内容走），剩下的再按序号接位置。
  这样插一条 / 删一条 / 换顺序都不会让周课的人工判定串位；描述重复时退化为按序号，不比原来差。
  残留边界：**把某条的描述整体改写成全新文本**时会被当成新行（那条的判定留在原行上）。
- **临时诊断放独立 partial 文件**（`KanbanPage.Stage6Diag.cs`）：
  验证完「删文件 + 删一行调用」就干净了，不用在正式文件里逐段掏。
  比阶段 4 那种「塞进页面里再删」更不容易留残渣。
- **靠 python 扫 dll 的字符串来判断第三方组件的 API**（`b'Events' in open(dll,'rb').read()`）：
  比翻文档/翻源码快得多，而且结论确定。找 `PMobileDatePicker` 在哪个程序集就是这么找到的。
